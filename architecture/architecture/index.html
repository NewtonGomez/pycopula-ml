    Architecture¶

    Objective¶

    The architecture separates six responsibilities:

    1. marginal modeling;
    2. dependence modeling with copulas;
    3. parameter estimation;
    4. dependence measures and pairwise weight matrices;
    5. graph construction from pairwise MI;
    6. future classification layers.

    The package is organized into independent domains:

    src/pycopula_ml/
├── copulas/
│   ├── base.py
│   └── parametrics/
│       ├── base.py
│       ├── frank.py
│       ├── clayton.py
│       ├── gaussian.py
│       ├── joe.py
│       ├── gumbel.py
│       └── ali_mikhail_haq.py
├── estimation/
│   └── maximum_likelihood.py
├── marginals/

    Statistical flow¶

    For two original variables \(X\) and \(Y\),

    \[ X \rightarrow \widehat F_X \rightarrow U, \]
    \[ Y \rightarrow \widehat F_Y \rightarrow V. \]

    The dependence model then evaluates

    \[ (U,V,\theta) \rightarrow C_\theta(U,V). \]

    If \(\theta\) is unknown, the estimation layer uses the sample log-likelihood

    \[ \ell(\theta) = \sum_{i=1}^{n} \log c_\theta(u_i,v_i) \]

    to obtain

    \[ \widehat{\theta} = \operatorname*{argmax}_{\theta} \ell(\theta). \]

    The full fitting workflow is therefore

    original data
    ↓
marginal transformation
    ↓
pseudo-observations (u, v)
    ↓
copula log-likelihood
    ↓
parameter estimation
    ↓
theta_hat

    This separation is deliberate.

    A copula should not need to know whether \(U\) and \(V\) came from:

    • a Normal marginal;
    • a Gamma marginal;
    • a Lognormal marginal;
    • an empirical CDF;
    • rank-based pseudo-observations.

    Likewise, the estimation layer should not contain the analytical density formula for every copula family. It operates through the common copula interface.

    Copula hierarchy¶

    BivariateCopula
└── Parametric bivariate copulas
    ├── FrankCopula
    ├── ClaytonCopula
    ├── GaussianCopula
    ├── JoeCopula
    ├── GumbelCopula
    └── AliMikhailHaqCopula

    The concrete class names and available exports depend on the active source version. All supported bivariate copulas share a common interface:

    • cdf();
    • pdf();
    • logpdf();
    • log_likelihood();
    • common input preparation and validation.

    The family-specific subclasses provide their probability formulas and parameter restrictions.

    Marginal hierarchy¶

    MarginalModel
├── EmpiricalMarginal
└── ContinuousMarginalModel
    └── ParametricMarginal

    MarginalModel defines:

    • fit()
    • cdf()
    • transform()

    ContinuousMarginalModel additionally requires:

    • pdf()
    • logpdf()

    This distinction matters because an empirical CDF is a step function and does not have an ordinary continuous density suitable for the same PDF interface.

    Model-selection layer¶

    MarginalSelector
├── MarginalCandidate
├── ParametricMarginal
└── MarginalFitResult

    MarginalSelector is responsible for:

    • fitting multiple candidate distributions;
    • recording failed candidates;
    • ranking successful candidates;
    • selecting by AIC, BIC, or KS statistic;
    • producing warnings;
    • transforming observations with the selected marginal.

    Estimation layer¶

    fit_copula_mle()
└── CopulaFitResult

    The estimation layer is responsible for:

    • validating pseudo-observations for likelihood evaluation;
    • evaluating candidate copula log-likelihoods;
    • minimizing the negative log-likelihood;
    • searching one or several bounded parameter intervals;
    • selecting the best successful solution;
    • returning statistical and numerical diagnostics.

    It is intentionally generic with respect to the copula family.

    The estimator requires a copula class or factory that can be called as

    copula(theta=<candidate>)

    and whose instances implement

    log_likelihood(u, v)

    This is why user code passes

    FrankCopula

    rather than an already instantiated

    FrankCopula(theta=...)

    to fit_copula_mle().

    Why estimation is not under tools¶

    A generic package path such as

    pycopula_ml.tools

    does not communicate the statistical responsibility of the code.

    Maximum-likelihood fitting belongs under

    pycopula_ml.estimation

    because it is part of the public statistical model-fitting API, not merely an internal utility.

    This also leaves room for future estimators such as:

    estimation/
├── maximum_likelihood.py
├── rank_based.py
└── ...

    without mixing statistical estimation with unrelated helpers.

    Dependence layer¶

    The pycopula_ml.dependence layer consumes existing fitted copulas and MLE results; it does not reimplement their density formulas or numerical optimization.

    Original feature matrix
          ↓
Rank-based pseudo-observations U
          ↓
Pairwise fit_copula_mle()
          ↓
Fitted copula for each feature pair
          ↓
mutual_information()
          ↓
CopulaWeightMatrices (L, Theta, M, weights)

    For supervised classification, this process is repeated for each class, using only its training observations. The returned matrices describe pairwise dependence between features. Maximum-spanning trees, conditional class scoring, and GNN architectures are not implemented by this layer.

    The Gaussian mutual-information branch uses a closed-form expression, while other continuous copulas use numerical quadrature. See Copula-based mutual information and Weight matrices.

    Design rule¶

    The classifier planned for later should not contain logic such as:

    if family == "frank":
    ...
elif family == "clayton":
    ...

    It should operate through a common copula interface.

    Similarly:

    • the copula layer should not decide which marginal distribution produced \(U\) and \(V\);
    • the estimation layer should not reimplement family-specific copula mathematics;
    • user scripts should not depend directly on the SciPy optimization backend.

    Separation of calculation and presentation¶

    Core statistical classes and functions return values and structured results.

    They should not depend on:

    • rich;
    • terminal formatting;
    • plotting;
    • interactive input.

    Presentation utilities can be added separately later.

    This keeps the statistical core usable from scripts, notebooks, tests, services, and future classifier components.

    Graph-construction layer¶

    graphs.chain.build_chain_graph() consumes a mutual-information matrix or CopulaWeightMatrices from dependence. It does not fit copulas, marginal distributions, or a classifier. The output ChainGraph provides the ordered vertex permutation, named edges, total MI, weighted adjacency, and an optional bidirectional edge_index NumPy array for graph-learning pipelines.

    The graph is a Hamiltonian path (one connected chain), not an unconstrained maximum spanning tree. Both provided algorithms are heuristics. A future classification module may use separate chains for each class, but such a classifier is not implemented by the current graph-construction API.

    See Chain graphs.
